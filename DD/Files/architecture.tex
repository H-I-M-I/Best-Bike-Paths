\subsection{Overview: High level components and their interaction}
% 2.1 Overview: High level components and their interaction

\paragraph{Purpose}
Best Bike Paths (BBP) is a client-server system that supports: trip recording and review, manual and automatic contribution of path issues, validation of auto-detected issues, path search with ranked alternatives, and merging/moderation of crowd-sourced path status. These capabilities are required by the assignment and are specified in the RASD scenarios and requirements.

\paragraph{System-level architecture (logical 3-tier)}
BBP follows a logical three-tier architecture (separation of responsibilities, not a deployment claim):
\begin{itemize}
	\item Presentation tier (Clients): mobile application that offers UI/UX for cyclists/users to record their trips, choose best path, report issues, etc., with an optional Admin Panel web app for moderators.
	\item Business tier (Backend): a modular monolith backend exposing REST APIs over HTTPS and implementing all BBP business rules (trip/issue/merge/ranking) as modules.
	\item Data tier (Storage \& caching): persistent storage for different entities (users, trips, ...); also a cache for read-heavy/expensive results.
\end{itemize}

BBP also relies on external providers (maps/routing, weather, traffic). These providers are outside the system boundary; the backend accesses them through dedicated adapter components (described below).

\paragraph{Architectural choice and rationale (modular backend + async support)}
BBP implements the business tier as a modular monolith: a single backend application whose internal modules align with major domain responsibilities (Trip, Issue/Validation, Aggregation/Moderation, Path Search/Ranking, Identity \& Access). This is well-suited for a startup/new application because it keeps the domain logic cohesive and easy to evolve while still enforcing clear boundaries between responsibilities.

The backend is complemented by asynchronous processing for tasks that are slow, bursty, or dependent on external services (e.g., enrichment and automatic detection). Instead of blocking interactive requests, the backend can enqueue work and let an internal worker execute it, improving responsiveness and robustness without requiring a fully distributed microservice architecture.

This solution is preferred over a microservices-based distributed architecture because BBP contains cross-cutting domain invariants—most notably the aggregation workflow that maintains a single publishable status per segment and resolves conflicts through confirmations and freshness—that are simpler to enforce when core domain updates occur within a single application boundary. Microservices could still realize the same functionality, but would typically introduce additional coordination mechanisms (messaging, idempotent event handling, and reconciliation) to keep derived “publishable” state aligned with incoming reports/confirmations, increasing design and operational complexity for a startup/new application. At the same time, the modular decomposition keeps boundaries explicit and enables future evolution towards independently deployable services if specific modules (e.g., detection/enrichment) require it.

\paragraph{Backend internal architecture (layers inside the Business tier)}
Within the backend (tier 2), the codebase is internally organized into layers (Interface, Domain, Repository and Adapter).

\paragraph{Asynchronous processing}
Some backend activities can take significant time and are not required to complete before the user receives a response. To keep interactive operations responsive, BBP executes these activities asynchronously: the backend records the core data immediately and schedules the additional processing to be handled in the background by a worker. In BBP this is primarily used to (i) enrich uploaded trips with weather/traffic context by contacting external providers without delaying the upload, and (ii) run automatic issue detection on the uploaded trip trace and later make the resulting candidate issues available to the user in the “items to confirm” workflow.

\paragraph{External services}
BBP relies on external providers that are outside the system boundary and are accessed by the backend through adapter components. These providers supply:
\begin{itemize}
	\item Map/Geocoding/Routing functionality (map visualization, geocoding/reverse-geocoding, route alternatives),
	\item Weather information (trip enrichment and optional ranking context),
	\item Traffic information (trip/path context and optional ranking or presentation).
\end{itemize}

\paragraph{Component structure and system boundary}
This section describes the main components of BBP and how they collaborate to deliver the system features. The component view follows the same logical three-tier structure introduced above: (i) a presentation tier (clients), (ii) a business tier (backend components that implement the application logic), and (iii) a data tier (persistence and caching). It also highlights where BBP interacts with external services outside the system boundary.

\centering

\caption{BBP component diagram (annotated)}
\label{fig:component_view}

\paragraph{Presentation tier (Clients)}
\begin{itemize}
	\item \textbf{Mobile App}: client application used by cyclists to record trips and navigate. It supports manual issue reporting and confirmation of automatically detected issues. The app stores a limited local state (e.g., trips and reports) to remain usable when connectivity is unavailable; once the network is restored, it synchronizes the pending data with the backend.
	\item \textbf{Admin Panel}: web interface reserved for moderators to handle unresolved conflicts and execute moderation actions.
\end{itemize}
Clients access BBP through a \textbf{public Client API} exposed by the backend.

\paragraph{Business tier (Backend)}
\begin{itemize}
	\item \textbf{Backend API}: exposes BBP REST endpoints over HTTPS using JSON. It validates incoming requests, enforces authentication and authorization, and routes valid requests to the core application logic.
	\item \textbf{Domain Core}: implements the application rules and manages the main workflows (e.g., trip management, issue lifecycle, and validation). It also performs aggregation and segment status updates, and supports path search features such as path ranking. Time-consuming operations that do not need to complete within the request/response cycle can be delegated to asynchronous processing.
	\item \textbf{Repository}: persistence boundary used by the Domain Core and background worker. It encapsulates access to the database and cache, keeping storage concerns separate from business logic.
	\item \textbf{Async Path (Queue + Worker)}:
	\begin{itemize}
		\item \textbf{Queue}: stores background jobs emitted by the Domain Core (e.g., enrichment and detection tasks).
		\item \textbf{Worker}: consumes jobs from the queue, executes the required processing, and persists results through the Repository.
	\end{itemize}
	\item \textbf{Adapter Layer (Gateway)}: integration boundary for third-party providers. It hides provider-specific APIs and formats, handles failures and retries as needed, and returns normalized data to backend components that require external information.
\end{itemize}

\paragraph{Data tier (Storage \& caching)}
\begin{itemize}
	\item \textbf{Database}: persistent storage for core entities such as users, trips, issues, confirmations, and the computed publishable segment status.
	\item \textbf{Cache}: used to reduce latency for read-heavy or expensive queries and to avoid repeated computation and repeated provider calls. The cache is accessed through the Repository; it may be refreshed or updated by background processes to keep frequently used data up to date.
\end{itemize}

\paragraph{External services (outside system boundary)}
BBP depends on external providers for:
\begin{itemize}
	\item \textbf{Maps \& Routing}: geocoding/reverse-geocoding, route alternatives, and other map-related data,
	\item \textbf{Weather}: trip enrichment and optional ranking context,
	\item \textbf{Traffic}: trip/path context and optional ranking or presentation.
\end{itemize}
These services are accessed only through the Adapter Layer.

\paragraph{Connectors and interactions}
\begin{itemize}
	\item \textbf{Client-to-backend}: the Mobile App and Admin Panel communicate with the Backend API via the public Client API using HTTPS (REST + JSON).
	\item \textbf{Synchronous backend flow}: the Backend API invokes the Domain Core for request handling; the Domain Core persists and retrieves state through the Repository.
	\item \textbf{Asynchronous backend flow}: the Domain Core enqueues background jobs to the Queue; the Worker consumes them, executes the processing, and stores outcomes via the Repository.
	\item \textbf{Third-party integrations}: external API calls are performed by the Adapter Layer, which contacts providers (Maps/Routing, Weather, Traffic) and normalizes their responses for backend use.
\end{itemize}

\paragraph{Constraints captured by the component view}
\begin{itemize}
	\item \textbf{No direct access to internal resources}: clients do not directly access the data tier or external services; all access is mediated by the backend (and, for third parties, through the Adapter Layer).
	\item \textbf{Persistence encapsulation}: persistence is primarily handled through the Repository (database + cache), keeping storage concerns separate from the Domain Core and background worker.
	\item \textbf{Third-party isolation}: all provider dependencies are isolated inside the Adapter Layer to limit coupling between the core system and external APIs.
	\item \textbf{Responsiveness}: time-consuming and non-interactive work is handled by the Queue/Worker path to keep request/response operations responsive.
\end{itemize}

\subsection{Selected architectural styles and patterns}
% 2.6 Selected architectural styles and patterns

BBP uses a set of simple design ideas that work well with the way it interacts with users. There are two main interaction modes: (i) when a user performs an action and BBP responds immediately, and (ii) when BBP performs work in the background without making the user wait. Consequently, BBP combines synchronous request/response for interactive operations with asynchronous background processing for work that can be safely deferred.

\paragraph{Synchronous interaction style (request/response)}
\begin{itemize}
	\item \textbf{Client--Server + RESTful API}: the Mobile App and the Admin Panel invoke backend functionality through a REST-like API over HTTPS/JSON. This covers the majority of interactive use cases (e.g., uploading/reviewing trips, reporting issues, confirming moderation actions, and searching for paths). This design keeps the clients decoupled from the backend implementation details and makes the system easier to evolve and maintain.
	\item \textbf{Logical three-tier architecture (Presentation--Business--Data)}: BBP is organized into three tiers: Presentation (clients), Business (backend logic), and Data (database and cache). This separation keeps the user interface concerns distinct from business rules and from storage details, improving understandability and maintainability.
	\item \textbf{Modular monolith backend}: the Business tier is implemented as a single deployable application with clear internal module boundaries. This supports cohesive behavior (e.g., consistent handling of publishable segment status) while keeping the backend evolvable as the system grows.
	\item \textbf{Layered backend (Controller--Service--Repository)}: internally, the backend follows a layered structure:
	\begin{itemize}
		\item \textbf{Controller/API} handles HTTP requests and access control.
		\item \textbf{Service/Domain} applies the business rules.
		\item \textbf{Repository} encapsulates data access to the database and cache.
	\end{itemize}
	This reduces coupling across concerns and keeps persistence details separate from the domain logic.
	\item \textbf{Adapter/Gateway pattern for external integrations}: external providers (e.g., maps and traffic updates) are accessed through an Adapter Layer. This centralizes provider-specific details and failures (timeouts, partial responses, format differences) so the rest of the system can remain simpler and more stable.
	\item \textbf{Caching (client-side and backend)}:
	\begin{itemize}
		\item \textbf{Client-side offline cache}: the Mobile App temporarily stores traces and reports on the device when connectivity is poor, and synchronizes them to the server when the network is available again. This keeps the user experience responsive even under intermittent connectivity.
		\item \textbf{Backend cache}: the Data tier includes caching for data that is read frequently or is expensive to compute or fetch. The cache is accessed through the Repository so caching does not leak into the business logic.
	\end{itemize}
\end{itemize}

\paragraph{Asynchronous interaction style (background processing)}
\begin{itemize}
	\item \textbf{Asynchronous messaging (Queue + Worker)}: BBP uses a queue/worker pattern for work that is slow, bursty, or not required to complete before responding to the user (e.g., enrichment and automatic detection). This preserves responsiveness for interactive operations and decouples request handling from background processing while still persisting outcomes through the same Repository path as the synchronous workflow.
\end{itemize}

\subsection{Other design decisions}
% 2.7 Other design decisions

\paragraph{Authentication and authorization policy}
Protected operations require an authenticated user session. Each request to the backend includes an authentication token transmitted securely over HTTPS. Moderator capabilities are exposed through the Admin Panel, and the backend enforces role-based authorization checks to ensure that only users with the appropriate role can execute privileged operations.

\paragraph{Offline synchronization policy}
The Mobile App applies a \emph{store-and-forward} strategy for trip tracks and reports: when offline, it stores data locally and forwards it once connectivity is restored. Client submissions are designed to be safe to retry (idempotent) using stable identifiers, so temporary connectivity issues do not result in duplicated records on the backend.

\paragraph{SegmentStatus consistency decision}
For each road segment, the system maintains a single shared \emph{SegmentStatus}. Incoming reports and confirmations update this status according to consistency rules. When the system observes conflicting or non-matching information, it flags the segment for manual review. This prevents the system from presenting different statuses for the same road at the same time and helps keep SegmentStatus accurate and up to date.

\paragraph{Background job execution semantics}
The Worker executes background tasks such as enrichment, detection, and periodic refresh. Background jobs are designed to be safely retryable and to persist their outcomes through the same Repository path used by synchronous workflows, ensuring results are durable and not lost if a job needs to be re-executed.

\paragraph{External-service resilience policy}
Calls to external services are performed defensively (timeouts and limited retries when safe). If optional context such as weather or traffic data cannot be retrieved, BBP still returns core results (e.g., route options) and marks the missing enrichment as unavailable rather than failing the entire request.

\paragraph{Caching policy}
Caching is applied only to read-heavy or expensive computations (e.g., reusable ranking inputs or frequently requested route-related results). Cached entries are refreshed or invalidated when the underlying SegmentStatus changes to reduce the risk of serving stale information.
