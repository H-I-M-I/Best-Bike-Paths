This section describes the design of the user interface of the \textit{Best Bike Paths (BBP)} system.
The user interface is conceived as a mobile application and is designed to support the interaction scenarios defined in the Requirement Analysis and Specification Document (RASD).
Given the context of use of the application, which is mainly during cycling activities, the interface prioritizes clarity, immediate feedback, and minimal user interaction while moving, delegating confirmation and editing tasks to moments when the user is stationary. 

\subsection{Overview}

The BBP user interface is centered around a map-based mobile view, which represents the primary interaction point between the user and the system.
Through the map interface, users can visualize bike paths, recorded trips, detected or reported issues, and suggested routes.
All core functionalities of the system, such as trip recording, path search, and path information contribution, are accessible through clearly identifiable actions available on the main interface.

\subsection{Key Screens and Workflows}

The user interaction with the BBP is organized over a set of principal screens which enable the core workflows presented in the RASD.
The main map interface shows that each player will start from the main point of cooperation, which is the main gate opened.

The usual method for recording a trip would begin with the user on the primary map page, where they would start to record their cycling.
While you take a trip, the recording interface projects your current path while minimizing user interaction.
Once the journey has finished, the user is taken to the problem confirmation screen, where automatically recognized problems can be reviewed before confirmation and publishing.

Path search is another important workflow.
By interacting with the main map screen, a user can input through the path search interface a start and end point of his or her bike travel and see one or more recommended paths that are ranked based on their fitness to meet the user's needs.
This process of manual path information input is treated in the same way as above, with a clear distinction between the main interface and the GUI specific for data insertion and confirmation.

\subsection{Interface Conventions and Legends}

The figures with the graphical user interfaces presented in this section set visual standards for showing information to the user.
These conventions are implemented in all the interfaces of the BBP mobile application and their summaries are provided to facilitate the understanding of what is depicted by certain graphics.

\paragraph{Path Color Coding}

Cycleways on the map are colored differently to indicate their class or function.
Green segments are trails marked as 'highly suitable' (based on a combination of user input and confirmed reports).
The yellow segments denote moderately suitable routes that pose minor or some restrictions.
Red lines indicate weak pathways, which means that there might be significant problems, or unsuitable habitat.
The colour coded pattern allows riders to instantly assess the potential quality of available routes.

\paragraph{Point Markers}

Markers are employed in the map to emphasize certain locations involving events or pertinent conditions therein.
The markers can depict automatically detected problems, bike-unfriendly situations reported by a user and other interesting items that might be along the bike path.
Each marker is set on the location at that geographic point, and looks different from path segments for users to catch their eye.

\paragraph{Issue and Obstacle Indicators}

Different marker shapes serve to indicate the different types of issues.
For instance, warning symbols may represent obstructions like potholes or road works, and location pins to place the position of detected or reported problems.
These indicators help the user learn about critical points on a path and appreciate what type of problem was reported.

\paragraph{Information Panels}

Information panels show more details or supplementary info about paths, problems or recording trips.
Such panels may have features like path name, length of the panel, estimated quality or type and severity of issue.
These panels convey structured context that empowers users to make decisions informed by the information, but without cluttering the map view.

\paragraph{Recording Status Indicators}

As recording is taking place, the user interface provides clear visual signs of which status the current recording is in.
Such cues can be indicator lights, status indicators of the recording devices or interface items that indicate the activation of the recording function.
This way, there is always feedback to the user if a cycling activity is being recorded.

\paragraph{Legend Box}

There is also a legend box on the interface; it summarizes the significance of colors, markers, and symbols used in the map.
This legend serves as a shorthand explanation that enables viewers to interpret the visual language of the application at-a-glance, without any extra instruction.

\subsection{Accessibility and Interaction Notes}

The BBP interface is especially mindful on the accessibility paradigm and takes into consideration mobile interaction limitations.
As the app is primarily used while riding a bike, the design reduces interactions to be as simple as possible through and in motion experience using big touch areas and immediate visual feedback.
Colour legend offers information on the path quality, but both coloured-text labels and typical legends values lead into that all information are meaningful in every color perception context.
Further, by processing confirmation and editing operations during times when the user has stopped moving, cognitive load is lowered, and safety is enhanced.
Such design considerations are intended to help keep the application usable in real-world usage scenarios.

\subsection{Navigation Flow}

The navigation among the different user interfaces is designed to be simple and coherent.
For the primary user interface, users can move to the trip recording screen to begin a cycling activity or path searching screen for route calculation.
After a tour is finished, users are directed to the issue confirmation interface to confirm auto-extracted information.
Supplementary features (e.g., input path manually and trip statistics) are available as clickable actions in the main interface.
This navigation framework provides easy access to the main functions of the BBP system, while maintaining a clear separation among the data collection, validation and display processes.
